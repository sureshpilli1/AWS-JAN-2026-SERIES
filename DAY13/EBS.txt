AWS EBS (Elastic Block Store) – Complete In-Depth Guide

1. What is Amazon EBS?
**Amazon Elastic Block Store (EBS)** is a **block-level storage service** designed to be attached to **EC2 instances**.
Unlike instance store volumes (which are ephemeral), EBS volumes persist beyond instance termination (if not deleted) and support features like snapshotting, encryption, and resizing.
Key characteristics:
* Acts like a **virtual hard disk**
* Used for **OS disks and application data**
* Data persists **independently of EC2 lifecycle**
* Can be detached and attached to another instance (within same AZ)
EBS is tightly integrated with EC2 and is one of the **most critical services** in AWS.

2. How Do We Measure EBS Volume Performance?
EBS performance is evaluated using **four main metrics**.
2.1 IOPS (Input/Output Operations Per Second)
IOPS represents:
* Number of read/write operations a volume can handle per second
Important:
* Small I/O operations → higher IOPS demand
* Databases are **IOPS-sensitive**
Example:
* 1,000 IOPS = 1,000 read/write operations per second
2.2 Block Size
Block size is the **amount of data transferred per I/O operation**.
Common block sizes:
* 4 KB
* 8 KB
* 16 KB
Impact:
* Smaller block size → more IOPS
* Larger block size → fewer IOPS, higher throughput
2.3 Latency
Latency is:
* Time taken to complete **one I/O operation**
Measured in:
* milliseconds (ms)
Lower latency = faster response
Critical for:
* Databases
* Transaction systems
* Real-time applications
2.4 Throughput
Throughput is:
* Rate at which data is transferred
Measured in:
* MB/s
* GB/s
Important for:
* Large file processing
* Data analytics
* Streaming workloads
2.5 Relationship Between IOPS, Throughput, and Block Size
A simplified formula:
IOPS = (Throughput × 1024) / Block Size (KB)
Meaning:
* Increasing block size increases throughput but reduces IOPS
* Workload type decides which metric matters more

3. EBS Volume Types – High-Level Classification
EBS volumes are broadly classified into:
* **SSD-backed volumes**
* **HDD-backed volumes**
* **Legacy magnetic volumes**
Each type is optimized for **specific workloads**.

4. Root Volume vs Additional Volumes
Root Volume
* Contains the **Operating System**
* Mandatory for launching an EC2 instance
* Without root volume → instance cannot boot
Supported root volume types:
* gp2
* gp3
* io1
* io2
Additional (Data) Volumes
* Used for application data, logs, databases
* Can be attached/detached independently
Supported additional volume types:
* gp2, gp3
* io1, io2
* st1, sc1
* standard (magnetic)

5. SSD-Based EBS Volumes
SSD volumes are optimized for **low latency and random I/O**.
5.1 General Purpose SSD – gp2 & gp3
These are the **most commonly used EBS volumes**.
gp2
* Balanced performance
* Performance scales with size
* Suitable for:
  * Boot volumes
  * Web servers
  * Dev/Test workloads
Size range:
* 1 GB to 16 TB
gp3 (Recommended)
* Decouples storage size from performance
* You can independently configure:
  * IOPS
  * Throughput
Size range:
* 1 GB to 64 TiB
Why gp3 is better:
* More predictable performance
* Lower cost
* Better control
5.2 Provisioned IOPS SSD – io1 & io2
Used when **exact IOPS guarantees** are required.
Suitable for:
* Databases
* High-transaction systems
* Mission-critical workloads
io1
* Provision specific IOPS
* Good for consistent high performance
* Size range: 4 GB to 16 TB
io2
* Higher durability
* Higher IOPS capability
* Designed for critical production systems
Key characteristics:
* Minimum IOPS: 100
* Maximum IOPS: up to 100,000
* Size range: 4 GB to 64 TiB

6. HDD-Based EBS Volumes
HDD volumes are optimized for **high throughput**, not random IOPS.
6.1 Throughput Optimized HDD – st1
Best suited for:
* Big data workloads
* Log processing
* Data warehousing
* Streaming large files
Characteristics:
* High MB/s throughput
* Not suitable for boot volumes
* Lower cost than SSD
Size range:
* 125 GB to 16 TB
6.2 Cold HDD – sc1
Designed for:
* Infrequently accessed data
* Cold storage
* Cost-sensitive workloads
Characteristics:
* Lowest performance
* Lowest cost
* Sequential access only
Size range:
* 125 GB to 16 TB

7. Magnetic (Standard) Volumes
Legacy storage option.
Characteristics:
* Lowest cost
* Lowest performance
* Rarely used today
Size range:
* 1 GB to 1 TB
Used only for:
* Legacy systems
* Very low-cost requirements

8. Availability Zone Limitation (Very Important)
An EBS volume:
* Exists in **one specific Availability Zone**
* Can be attached only to EC2 instances in the **same AZ**
If AZ differs:
* Volume cannot be attached
* Snapshot must be used to move data across AZs

* Keep root volume separate from data
* Always tag volumes
* Take snapshots before resizing
* Monitor IOPS and throughput in CloudWatch

what is block level storage:
---------------------------

Block-level storage is a type of storage in which data is stored and accessed in fixed-size units called blocks.
In simple words, imagine a hard disk divided into thousands or millions of small blocks. Each block has its own address, and the operating system can read or write data to individual blocks.
Let's understand this using AWS EBS.
1. What is a block?
Imagine you have a 100 GB hard disk.
Internally, the storage is divided into smaller units called blocks.
Each block can be addressed independently.
When you save a file, the operating system's filesystem manages how the file's data is placed across these blocks.

2. What is a block-level storage device in AWS?
In AWS, Amazon EBS (Elastic Block Store) is a block-level storage service.
Suppose you create:
- EC2 instance: Ubuntu Linux
- EBS volume: 20 GB
You attach the EBS volume to the EC2 instance.
Linux detects it as a block device, for example:
/dev/nvme1n1
You can check it using:
lsblk
You can then create a filesystem on it, mount it and store files.
Example commands:
# Create filesystem
sudo mkfs -t ext4 /dev/nvme1n1
# Create mount directory
sudo mkdir /data
# Mount the volume
sudo mount /dev/nvme1n1 /data
Now you can store files inside /data.
Important: These commands are examples. Never run mkfs on a device containing data you want to preserve. Confirm the correct device first.
3. How does block-level storage work?
Consider saving a 10 MB file.
1. You create a file in Linux.
2. The filesystem divides the file's data into blocks.
3. Those blocks are written to the EBS volume.
4. When you open the file, Linux reads the required blocks from the EBS volume.
The operating system and filesystem manage this process.
4. Block storage vs File storage vs Object storage
This is an important DevOps and AWS interview topic.
1. Block storage – Amazon EBS
Stores data in addressable blocks. The operating system manages the filesystem.
Example: EC2 root volume, database disk.
2. File storage – Amazon EFS
Stores data in files and directories.
Example: Shared files accessed by multiple EC2 instances.
3. Object storage – Amazon S3
Stores data as objects inside buckets.
Example: Images, videos, backups and log archives.





what are SSD and HDD 
--------------------

HDD and SSD are two types of storage devices used in computers, laptops and servers. Both are used to store data, but they use different technologies.

Let's understand them from the basics.
1. HDD – Hard Disk Drive
HDD stands for Hard Disk Drive.

It is a traditional storage device that stores data using magnetic technology.

Inside an HDD, there are rotating magnetic disks (called platters) and a read/write head.
How does it work?
1. HDD contains circular disks called platters.
2. These platters are coated with magnetic material.
3. The platters rotate at high speed.
4. A read/write head reads and writes data by magnetically changing areas on the platter.
5. Data remains stored even when the power is switched off.
For example, when you save a movie on an HDD, the data is magnetically recorded on its platters.
2. What is magnetic storage?
Magnetic storage means storing information by changing the magnetic properties of a material.
Think of a small magnet.
- One magnetic state can represent binary 0.
- Another magnetic state can represent binary 1.
Computers use these binary values to store information.
HDDs use this principle to store data.
Other examples of magnetic storage:
- HDD
- Magnetic tape
- Floppy disk

3. SSD – Solid State Drive
SSD stands for Solid State Drive.
Unlike HDD, SSD does not contain rotating disks or moving mechanical parts.
It stores data using electronic memory chips called NAND flash memory
How does it work?
1. SSD contains memory chips.
2. These chips store electrical charge in memory cells.
3. The presence or absence of charge (or different charge levels) represents data.
4. Data can be read and written electronically.
5. No rotating disk or mechanical read/write head is required.
Even when power is switched off, the stored data remains.





FILE SYSTEM CONCEPTS:
--------------------
1. First, understand the complete storage process
Suppose you create an additional 20 GB EBS volume in AWS and attach it to your Ubuntu EC2 instance.
You cannot immediately use it like a normal folder. There are a few steps.
How a new disk becomes usable
1. EBS volume
   
   AWS provides a 20 GB virtual disk.
2. Block device
   
   Linux detects the disk, for example /dev/nvme1n1.
3. Create a filesystem
   
   Format the disk with XFS or ext4.
4. Create a mount point
   
   Create a directory such as /data.
5. Mount the disk
   
   Connect the filesystem to /data.
6. Store files
   
   Now you can save files inside /data.

Now let's understand each step.

2. What is a filesystem?
A filesystem is a method used by an operating system to organize, store, retrieve and manage data on a storage device.
Imagine you purchase a new cupboard.
The cupboard is empty. You need to arrange shelves, create sections and organize your clothes.
Similarly, when you attach a new disk to Linux, it initially may not have a filesystem.
Linux needs a filesystem to organize data into files and directories.
For example:
- Create files.
- Create folders.
- Read files.
- Write files.
- Delete files.
- Track where data is stored.
Without a filesystem, Linux cannot use the disk as a normal file-and-directory storage location.

3. What are ext4 and XFS?
ext4 and XFS are two different types of Linux filesystems.
ext4
Fourth Extended Filesystem.
XFS
High-performance 64-bit journaling filesystem.
Both are used to manage files and directories in Linux.

Which one should you choose?
- ext4: Good general-purpose choice.
- XFS: Good choice for workloads involving large files and high throughput.
Both are commonly used with AWS EBS.

4. What does creating a filesystem mean?
Creating a filesystem means preparing a disk or partition with a filesystem structure.
This process is also commonly called formatting.
For example, to create an ext4 filesystem:
sudo mkfs -t ext4 /dev/nvme1n1
Command	      Meaning
sudo	         Execute with administrator privileges
mkfs	         Make filesystem
-t	           Specify filesystem type
ext4	         Filesystem type
/dev/nvme1n1	 Target block device
If you want XFS instead:
sudo mkfs -t xfs /dev/nvme1n1
Important warning: mkfs creates a new filesystem and can destroy existing data. Never execute it on a disk containing data you need to preserve. Check the device carefully first.

5. What is a mount point?
A mount point is a directory in Linux where you make a storage device accessible.
For example, you have an additional 20 GB EBS volume.
You create a directory:
sudo mkdir /data
Here:
- mkdir = Make directory.
- /data = Directory created under the root filesystem.
Now /data is an empty directory. It is not yet connected to your new EBS volume.
You need to mount the volume.

6. What does mounting mean?
Mounting means attaching a filesystem to a directory in the Linux directory structure so that you can access its files.
For example:
sudo mount /dev/nvme1n1 /data
This means:
- /dev/nvme1n1 = Storage device.
- /data = Mount point.
After mounting:
Linux EC2 instance
       |
       |
       ├── /
       |    |
       |    ├── home
       |    ├── etc
       |    ├── var
       |    └── data  ← Additional EBS volume mounted here
       |                  |
       |                  ├── file1.txt
       |                  ├── file2.txt
       |                  └── folder1


Now you can save files:
sudo touch /data/file1.txt
You can check:
ls /data

You should see:
file1.txt
Important: Mounting does not mean copying data from one disk to another. It makes the filesystem on the disk accessible through a directory.

Let's examine each command individually.
Command 1: lsblk
lsblk

For example:

nvme0n1       259:0    0   20G  0 disk
├─nvme0n1p1   259:1    0   20G  0 part /
nvme1n1       259:2    0   20G  0 disk


Let's understand this output:
Name	         Meaning
nvme0n1	      First disk
nvme0n1p1	    First partition of first disk
nvme1n1	      Second disk
20G	          Disk size
disk	         Whole disk
part	         Partition
/	            Mounted at root directory

Notice:
- nvme0n1 is your first disk.
- nvme0n1p1 is a partition of that disk.
- / means that partition is mounted as the root filesystem.
- nvme1n1 is another disk, which is not mounted yet.


You can use:
lsblk -f
This displays additional filesystem information, such as:
- Filesystem type
- UUID
- Filesystem label
- Mount point

Command 2: df -Th
df -Th
Full meaning:
- df = Disk Free.
- -T = Display filesystem type.
- -h = Human-readable sizes (GB, MB, KB).
This command displays filesystem disk space usage.

Example:

/dev/root        ext4    20G   8G    11G  43%  /
/dev/nvme1n1     xfs     20G   1G    19G   5%  /data

Let's understand the columns:
Column	          Meaning
Filesystem	      Device or filesystem name

Size	            Total filesystem size
Used	            Space already consumed
Avail	           Available space
Use%	            Percentage of space used

Example:

Suppose your EBS volume is 20 GB.
- Total size = 20 GB
- Used = 5 GB
- Available = 15 GB
- Usage = 25%
You can check the usage of a particular directory:
df -Th /data

Command 3: file -s /dev/nvme1n1
sudo file -s /dev/nvme1n1
This command is particularly useful when working with newly attached EBS volumes.
Let's break it down:
Part	Meaning
file	Identifies the type of a file or device
-s	Examines special/block device files
/dev/nvme1n1	Device being examined

Why do we use it?
Suppose you attach a new EBS volume to EC2.
You want to know:
Does this disk already contain a filesystem, or is it a blank disk?

Run:
sudo file -s /dev/nvme1n1

Possible output 1:
/dev/nvme1n1: data
This often indicates that the device does not have a recognizable filesystem signature.

Possible output 2:
/dev/nvme1n1: SGI XFS filesystem data
This indicates that an XFS filesystem is present.

Possible output 3:
/dev/nvme1n1: Linux rev 1.0 ext4 filesystem data
This indicates that an ext4 filesystem is present.

Important
 file -s is an identification command. It does not create a filesystem or format the disk.
Also, data alone is not absolute proof that a disk is empty. Check its partitions and signatures before formatting.

This is an important interview question.

file -s	What type of data or filesystem signature is present on a device?

  ↓

  ↓

9. What is a partition?
A partition means dividing a physical or virtual disk into separate logical sections.
Suppose you have a 100 GB disk.
You can divide it into:
100 GB Disk
    |
    ├── Partition 1 → 50 GB
    |
    └── Partition 2 → 50 GB


Linux identifies partitions using names such as:
/dev/nvme1n1       → Entire disk
/dev/nvme1n1p1     → First partition
/dev/nvme1n1p2     → Second partition

You can create a filesystem directly on an entire disk or on a partition.
For many Linux setups, partitions are used, but a separate EBS data volume can also have a filesystem directly on the whole device.

10. Complete practical example using AWS EBS
Let's imagine you have:
- EC2 instance: Ubuntu
- Root EBS volume: 20 GB
- Additional EBS volume: 20 GB
You want to use the additional EBS volume for storing application data.
Your EC2 storage
Root EBS – 20 GB

/dev/nvme0n1 → /
Already mounted

Additional EBS – 20 GB

/dev/nvme1n1 → Not mounted yet
Needs setup


Follow these steps.

Step 1: Identify the disk
lsblk


Find your additional disk.

Step 2: Check whether a filesystem exists
sudo file -s /dev/nvme1n1


If it is a new, blank disk, you may see:
/dev/nvme1n1: data


Step 3: Create an ext4 filesystem

Only after confirming that this is the correct, unused disk:
sudo mkfs -t ext4 /dev/nvme1n1

Step 4: Create a mount point
sudo mkdir /data

Step 5: Mount the disk
sudo mount /dev/nvme1n1 /data

Step 6: Verify the mount
df -Th

You should see something similar to:
Filesystem       Type   Size  Used Avail Use% Mounted on
/dev/nvme0n1p1   ext4    20G    8G   11G  43%  /
/dev/nvme1n1    ext4    20G   24M   19G   1%  /data

Step 7: Store a file
sudo touch /data/test.txt

Check:
ls /data

Output:
test.txt
Congratulations! Your additional EBS volume is now usable.

11. What is unmounting?
Unmounting means disconnecting a mounted filesystem from its mount point.
For example:
sudo umount /data
After unmounting:
- The EBS volume is still attached to EC2.
- The filesystem still exists.
- The data is still stored on the volume.
- You cannot access that filesystem through /data until you mount it again.
To mount it again:
sudo mount /dev/nvme1n1 /data
Before unmounting, make sure applications are not actively using the filesystem.

12. What happens after restarting EC2?
There is one more important concept.
If you mount a volume using:
sudo mount /dev/nvme1n1 /data
the mount generally does not automatically survive a reboot.
To make it persistent, Linux uses a configuration file called:
/etc/fstab

You can use the filesystem UUID rather than relying on a device name.
Find the UUID:
sudo blkid /dev/nvme1n1

Example output:
/dev/nvme1n1: UUID="1234-abcd" TYPE="ext4"


Then add an entry to /etc/fstab:
UUID=1234-abcd  /data  ext4  defaults,nofail  0  2


This tells Linux to mount the filesystem at /data during startup.

The nofail option helps the system continue booting if the additional volume is unavailable.

Test the configuration before rebooting:
sudo mount -a
For production systems, verify the UUID and filesystem type carefully before editing /etc/fstab.
