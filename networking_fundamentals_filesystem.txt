CIDR:
The masking system did not change. What changed was the way networks are allocated and represented.
Think of it this way:
Old (Classful Networking)
The network size was determined by the IP class.
Class	Default Mask
A	255.0.0.0 (/8)
B	255.255.0.0 (/16)
C	255.255.255.0 (/24)
Example:
192.168.1.10
People automatically assumed:
255.255.255.0
because it was a Class C address.
Problem
Suppose a company needs:
500 hosts
Class C:
254 hosts
Too small.
Class B:
65,534 hosts
Too large.
Huge waste of IP addresses.

Modern (CIDR)
CIDR removed the restriction that networks must be only:
/8
/16
/24

Now you can use:
/20
/21
/22
/23
/25
/26
/27
...

whatever size you need.
Example:

Mask:

This would have been impossible in the old classful system.


If the subnet mask concept stayed the same, how did networking change from Class A/B/C to CIDR?
The answer is:
Routers stopped assuming the mask based on the IP class and started carrying the mask information explicitly.

Old Classful Networking
Suppose you saw:
192.168.1.10
Router automatically thought:
192 = Class C
Class C = /24
Mask = 255.255.255.0
No need to specify the mask.
The router assumed it.

CIDR Idea
Instead of saying:
192.x.x.x = always /24
CIDR says:
Don't assume anything.
Always specify the prefix.
Examples:
192.168.1.0/23
192.168.1.0/25
192.168.1.0/27
All are valid.

What Changed in Routers?
Old router:
IP starts with 192
      ↓
Must be Class C
      ↓
Must be /24

CIDR router:
Network = 192.168.1.0/27
The router stores:
Network Address
+
Prefix Length
and no longer cares about classes.

Example
Classful world:
172.16.0.0
Automatically:
Class B
Mask = /16

CIDR world:
172.16.0.0/20
Mask:
255.255.240.0
Perfectly valid.
Even though it is not a Class B default mask.

What Changed?
Before
The mask was implied by the class.
10.x.x.x     → /8
172.x.x.x    → /16
192.x.x.x    → /24

After CIDR
The mask is explicitly specified.
10.0.0.0/22
10.0.0.0/19
10.0.0.0/27
No assumptions.

CIDR became possible because routers stopped deriving the subnet mask from the IP address class and instead started using an explicitly provided prefix length (such as /20 or /27). 
The subnet mask itself did not change; only the rule for determining it changed.

STATELESS AND STATEFUL APPLICATIONS:
-----------------------------------

1. Stateless application
A stateless application does not keep the user's session/state in the application server between requests.

2. Stateful application
A stateful application remembers information about the client/session between requests.
A very important example: shopping cart

Stateless = "I don't need to remember you on this server."
Stateful = "I need to remember something about you between requests."
And one especially important DevOps point:
Stateless application ≠ application with no data.
It means the application instance doesn't rely on its own local memory/storage to preserve client state. Persistent data can be kept in external systems such as databases or Redis.

| Stateless                                    | Stateful                                 |
| -------------------------------------------- | ---------------------------------------- |
| Doesn't depend on server-local session state | Depends on stored session/state          |
| Each request can be handled independently    | Requests may depend on previous requests |
| Easier to scale horizontally                 | Scaling can be more complicated          |
| Any server can usually handle the request    | May need the same server or shared state |
| Common in REST APIs                          | Common in session-based applications     |
| Good fit for containers/Kubernetes           | Requires careful state management        |

what happens when an application gets more traffic that is placed in a single server
------------------------------------------------------------------------------------
When an application receives more traffic than a single server can handle, the server may become overloaded, the application becomes slow, and eventually requests may fail. 
Let's understand why and how DevOps engineers solve this problem.

Why does the server become overloaded?
1. CPU reaches its limit
The server has to execute application code for incoming requests. More requests require more processing. If CPU capacity is exhausted, requests take longer to complete.
2. RAM becomes insufficient
Applications need memory for objects, request data, caches and connections. If memory is exhausted, the operating system may terminate processes, or the application may crash.
3. Database becomes a bottleneck
Many requests may query the same database. Database connections, CPU, disk I/O or query performance can become limiting factors—even if the application server still has spare capacity.
4. Requests form a queue
When requests arrive faster than the server can process them, they wait. Waiting increases response time, and eventually requests may time out.

How do DevOps engineers solve this problem?
There are two common approaches.
Option A: Vertical scaling — make one server bigger
This is called vertical scaling. It can be simple, but it has limits: a single server can still fail, and the largest server has finite capacity.
Option B: Horizontal scaling — add more servers
This is called horizontal scaling.

In AWS, a common architecture is:
- Application Load Balancer (ALB): distributes HTTP/HTTPS requests across healthy application servers.
- Auto Scaling Group (ASG): adds or removes EC2 instances according to configured scaling policies.
- CloudWatch: monitors metrics such as CPU utilization and request counts.
- Database scaling and caching: help prevent the database from becoming the next bottleneck.
In Kubernetes, you might scale application Pods using HPA and add worker nodes using Cluster Autoscaler or EKS node autoscaling.

5. One important thing to remember
Adding more application servers does not automatically solve every bottleneck. If all servers depend on one overloaded database, the database can still slow down the whole application.

In summary: more traffic means more work. When demand exceeds the capacity of the server or another component, response times rise and failures may occur.
DevOps engineers monitor the bottleneck and scale vertically or horizontally, while improving the application, database and caching as needed.

what is block level storage:
---------------------------

Block-level storage is a type of storage in which data is stored and accessed in fixed-size units called blocks.
In simple words, imagine a hard disk divided into thousands or millions of small blocks. Each block has its own address, and the operating system can read or write data to individual blocks.
Let's understand this using AWS EBS.
1. What is a block?
Imagine you have a 100 GB hard disk.
Internally, the storage is divided into smaller units called blocks.
Each block can be addressed independently.
When you save a file, the operating system's filesystem manages how the file's data is placed across these blocks.

2. What is a block-level storage device in AWS?
In AWS, Amazon EBS (Elastic Block Store) is a block-level storage service.
Suppose you create:
- EC2 instance: Ubuntu Linux
- EBS volume: 20 GB
You attach the EBS volume to the EC2 instance.
Linux detects it as a block device, for example:
/dev/nvme1n1
You can check it using:
lsblk
You can then create a filesystem on it, mount it and store files.
Example commands:
# Create filesystem
sudo mkfs -t ext4 /dev/nvme1n1
# Create mount directory
sudo mkdir /data
# Mount the volume
sudo mount /dev/nvme1n1 /data
Now you can store files inside /data.
Important: These commands are examples. Never run mkfs on a device containing data you want to preserve. Confirm the correct device first.
3. How does block-level storage work?
Consider saving a 10 MB file.
1. You create a file in Linux.
2. The filesystem divides the file's data into blocks.
3. Those blocks are written to the EBS volume.
4. When you open the file, Linux reads the required blocks from the EBS volume.
The operating system and filesystem manage this process.
4. Block storage vs File storage vs Object storage

what are SSD and HDD 
--------------------

HDD and SSD are two types of storage devices used in computers, laptops and servers. Both are used to store data, but they use different technologies.

Let's understand them from the basics.
1. HDD – Hard Disk Drive
HDD stands for Hard Disk Drive.

It is a traditional storage device that stores data using magnetic technology.

Inside an HDD, there are rotating magnetic disks (called platters) and a read/write head.
How does it work?
1. HDD contains circular disks called platters.
2. These platters are coated with magnetic material.
3. The platters rotate at high speed.
4. A read/write head reads and writes data by magnetically changing areas on the platter.
5. Data remains stored even when the power is switched off.
For example, when you save a movie on an HDD, the data is magnetically recorded on its platters.
2. What is magnetic storage?
Magnetic storage means storing information by changing the magnetic properties of a material.
Think of a small magnet.
- One magnetic state can represent binary 0.
- Another magnetic state can represent binary 1.
Computers use these binary values to store information.
HDDs use this principle to store data.
Other examples of magnetic storage:
- HDD
- Magnetic tape
- Floppy disk

3. SSD – Solid State Drive
SSD stands for Solid State Drive.
Unlike HDD, SSD does not contain rotating disks or moving mechanical parts.
It stores data using electronic memory chips called NAND flash memory
How does it work?
1. SSD contains memory chips.
2. These chips store electrical charge in memory cells.
3. The presence or absence of charge (or different charge levels) represents data.
4. Data can be read and written electronically.
5. No rotating disk or mechanical read/write head is required.
Even when power is switched off, the stored data remains.

2. What is a filesystem?
A filesystem is a method used by an operating system to organize, store, retrieve and manage data on a storage device.
Imagine you purchase a new cupboard.
The cupboard is empty. You need to arrange shelves, create sections and organize your clothes.
Similarly, when you attach a new disk to Linux, it initially may not have a filesystem.
Linux needs a filesystem to organize data into files and directories.
For example:
- Create files.
- Create folders.
- Read files.
- Write files.
- Delete files.
- Track where data is stored.
Without a filesystem, Linux cannot use the disk as a normal file-and-directory storage location.

3. What are ext4 and XFS?
ext4 and XFS are two different types of Linux filesystems.
ext4
Fourth Extended Filesystem.
XFS
High-performance 64-bit journaling filesystem.
Both are used to manage files and directories in Linux.

Which one should you choose?
- ext4: Good general-purpose choice.
- XFS: Good choice for workloads involving large files and high throughput.
Both are commonly used with AWS EBS.

Creating a filesystem means preparing a disk or partition with a filesystem structure.

Unmounting means disconnecting a mounted filesystem from its mount point.

- The data is still stored on the volume.

There is one more important concept.

/etc/fstab

You can use the filesystem UUID rather than relying on a device name.
Find the UUID:
sudo blkid /dev/nvme1n1

Example output:
/dev/nvme1n1: UUID="1234-abcd" TYPE="ext4"


Then add an entry to /etc/fstab:
UUID=1234-abcd  /data  ext4  defaults,nofail  0  2


This tells Linux to mount the filesystem at /data during startup.

The nofail option helps the system continue booting if the additional volume is unavailable.

Test the configuration before rebooting:
sudo mount -a
For production systems, verify the UUID and filesystem type carefully before editing /etc/fstab.
